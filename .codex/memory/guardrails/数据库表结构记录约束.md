# 业务数据库表结构记录约束

## 必须遵守

1. 业务数据库表结构只写入 `modules`，不得写入 `library`、`plans` 或 `changes` 作为当前结构的唯一记录。
2. 每条表记录必须标明来源类型：`user_material` 或 `code_sql`。
3. 每条表记录必须包含表名、表注释、表作用、字段名、字段类型和字段注释；缺失项必须明确标记为“未确认”，不得自行补全。
4. 发现字段依赖其他表时，必须记录当前字段、目标表、目标字段和关联用途；没有证据不得创建关系。
5. 表的作用可以通过理解补充，但必须基于可定位的 SQL、代码、数据库或用户材料，并将推断标记为 `derived` 或待确认。
6. 项目表总量超过 200 张后，才按功能模块建立表目录；未达到阈值时不得为了形式拆分大量目录。
7. 同一张表只能有一个权威记忆条目；跨模块引用使用稳定 `memory_id`，不得复制多份结构。
8. 表结构变更后必须同步更新直接索引和祖先索引；重要变更另写 `changes` 条目。

## 建表决策约束

1. 建表前先检查当前项目已有业务表、迁移脚本、Mapper/XML、实体映射和索引写法；存在可比表时，优先沿用当前项目实际风格。
2. 当前项目没有可比表时，采用精简的阿里巴巴数据库规范基线，并按目标数据库产品和版本转换为可执行方言；不复制与当前功能无关的完整规范。
3. 先确定当前功能真正需要的业务字段，再按功能组说明字段的作用和本表创建目的。至少说明业务身份组、业务属性组，以及实际采用的公共字段组。
4. 审计、状态/生命周期、租户/组织隔离、逻辑删除、扩展和乐观锁等字段组都不是默认必选项；没有当前需求、既有项目风格或证据支持时不创建。
5. 使用 `version` 等乐观锁字段时，必须解释它用于检测并发修改版本、避免后写覆盖先写，以及本表为什么需要它。
6. 人员、组织等表中，姓名、年龄等字段只在当前页面、接口、查询或业务规则实际需要时创建；不因“常见字段”自动扩展。
7. 输出建表设计或 DDL 前，列出已选择的字段组、作用、创建目的、必要性，以及明确未创建的字段组和原因。
8. 只创建当前任务需要的表、字段、约束和索引；不顺手设计未来模块、全库公共字段或无关关联表。

## 来源与冲突

- `.codex/source-materials/` 中的用户原始材料用于记录设计意图和业务说明；
- 代码中的可执行 SQL、迁移脚本和实际数据库用于确认当前实现；
- 来源冲突时不得静默覆盖，应记录冲突并优先采用当前实现；
- 只有推测、无法定位来源或尚未核验的内容，状态必须为 `draft`、`derived` 或待确认。

## 禁止事项

- 禁止把密码、Token、连接串、完整业务数据或敏感样例写入表结构记忆；
- 禁止根据字段名相似、名称习惯或模型猜测创建外键关系；
- 禁止用旧的表记录覆盖当前 SQL 或数据库事实；
- 禁止把数据库表记忆当作 DDL、迁移脚本或数据库变更操作的替代品；
- 禁止为了“完整”复制整个 SQL、ORM 文件或全库无关表结构。

## 完成检查

写入或更新前确认：

- 表名和字段名来自可定位来源；
- 表作用与关联关系有证据或已标记推断；
- 来源类型、路径、定位、状态和更新时间齐全；
- 没有重复表条目、敏感数据或无关全库信息；
- 大型项目只有在表总量超过 200 张时才按功能模块拆分。
