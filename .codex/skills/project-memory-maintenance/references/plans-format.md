# 大需求计划格式

## 创建条件

`plans` 只保存两类详细计划：

- 材料中的大需求：用户要求处理的需求文档或阶段需求包，包含一组交付事项，需要持续一段时间或分阶段实施。来源通常位于 `.codex/source-materials/`，记录实际路径和章节。
- 复杂问题：即使来源在对话中，也确实需要分阶段处理，且有依赖、重要待确认项或独立验收安排。记录复杂性依据和用户目标；没有来源文件时明确写“对话需求，无材料文档”，不伪造文件。

仅把文件放进材料目录，不等于要求实施其中所有内容。单纯读取材料、普通问答、改按钮名称/文案/样式、局部字段展示、当轮可完成的简单修复，不创建计划或日期日计划。“先列计划”可以只在会话中列步骤，不自动触发持久计划。问题涉及数据库、接口或权限本身不代表必须建计划，应判断实际是否需要持续的范围、依赖和验收管理。

创建前检索 `plans/INDEX.md` 和已有计划；同一需求的澄清、补充和后续实施优先更新原计划，不按对话轮次重复建文件。计划记录预期和进度，不替代当前代码事实，不因本流程自行增加其他层的写入。

## 文件名与版本

- 文件名只用 `YYYY-MM-DD-vN.md`，例如 `2026-10-09-v1.md`，直接保存于 `plans/`。
- 日期是该版本形成的日期；普通进度更新不改日期、文件名或版本号。
- 首次形成计划优先使用 `v1`。需求范围、实施方案或关键约束发生实质变化时形成更高版本，保留旧版、写明差异，并在新版头部通过 `supersedes` 指向被替代文件；反向关系从新版推导，不维护 `superseded_by`。
- 同日已有同名文件时，选用未占用的更高 `vN`；同一需求的后续版本号还必须高于该需求的已有版本。不得覆盖另一个需求。编号只保证文件唯一，需求归属通过稳定 `plan_id` 判断。
- 同一大需求跨版本保持 `plan_id`，例如 `PLAN-20261009-001`；文件头不再另存 `memory_id`，派生索引根据 `plan_id` 和文件名生成唯一版本节点标识。
- 需求清单中的 `REQ-001` 等编号在该计划各版本中保持稳定，删除的需求标记取消，不复用编号。
- `plans/INDEX.md` 每个文件只保留一句需求简介、计划编号、版本/状态和日期，不索引每条需求。旧版明确标记“已被替代”，执行时选择同一 `plan_id` 的当前有效版本。

## 轻量文件头

需求正文文件只保留三个必填字段：

```yaml
---
plan_id: PLAN-20261009-001
plan_state: active
updated_at: 2026-10-09
---
```

- `plan_id`：需求的稳定编号，跨版本不变；新需求使用新的编号。
- `plan_state`：整份计划的当前状态，不等于单条需求进度或事实证据状态。
- `updated_at`：本文件最后一次实质维护日期；只查看文件不刷新。
- 仅替代旧版本时增加 `supersedes: 2026-10-09-v1.md`；首次建计划不写占位值。

版本形成日期和版本号从 `YYYY-MM-DD-vN.md` 读取；标题从正文读取，来源、范围、影响和进度保留在正文。不要重复添加 `memory_id`、`type`、`status`、路径、别名、哈希、Git 核验字段或反向替代字段。`INDEX.md` 是导航文件，继续使用索引元数据，不套用需求文件头。

派生索引自动生成 `plan_id@YYYY-MM-DD-vN` 版本节点 ID，并推导类型、路径、标题和内容哈希；以 `plan_id` 精确检索需求，默认排除 `cancelled`、`superseded`。计划不是当前代码事实，代码新鲜度检查标记 `not_applicable`，不要求 `verified_commit` 或头部证据字段；读取时仍核对正文来源、依赖、待补充及验收结果，不能据此宣称实现已核验。

## 状态与来源

使用 [详细计划模板](../assets/requirement-plan-template.md)。`plan_state` 使用 `draft`、`active`、`blocked`、`completed`、`cancelled`、`superseded`。

- 初始来源可追溯但存在关键待确认项时使用 `draft`；已有明确范围和可实施事项时使用 `active`。
- `blocked` 表示当前整体没有可推进事项；部分需求被阻塞时仅标记这些清单行，不把整个计划一概阻塞。
- `completed` 要求已纳入范围的需求满足验收条件；“代码完成”“测试通过”“已部署”“验收完成”分别记录，不互相替代。
- 来源记录文件路径、版本/日期或已计算的哈希、章节/页码及对应需求编号。对话来源记录用户目标和已确认决策；未知的信息写明缺口，不杜撰时间、来源路径或已确认结果。
- 与现状有关的代码事实引用已核验的 `modules` 或实际来源，不复制整套页面记忆。来源文档变化时只复核相关需求、清单和待补充项；不改写原材料。

## 详细正文

保留下列章节；不适用的章节写“不涉及”及依据，不为填满模板虚构表结构、依赖或风险。

1. **需求来源文档**：实际来源位置、版本、定位信息，以及需求来自哪个文档/章节；复杂问题无文档时记录对话来源。
2. **需求目标与范围**：本阶段要达成的业务结果、交付物和不在本阶段的内容。
3. **需求计划清单**：逐条记录需求编号、描述、明确性、可立即实施及原因、当前进度、阻塞项和可检查的验收条件。需求明确性、实施就绪性和完成进度分别记录；不凭估计填完成百分比。
4. **当前现状与影响范围**：已核验的相关页面、接口、模块或环境，以及会被影响的旧行为；未核验部分明确标注。
5. **需求计划表结构**：列出新增、修改、删除和引用的表，目的、关联需求、字段/关联变化、现有数据处理、接口影响和迁移/回滚安排。引用已有表不等于改表。设计字段时继续遵守项目已有数据库设计规则；现有表未经核验则列为待补充。
6. **需求待补充**：每个问题单独编号，列影响等级、已知信息、缺失信息、影响范围、依赖的 REQ-ID、确认方及确认结果。
7. **依赖与前置条件**：前序需求、接口、数据、权限、外部系统、测试/部署环境等依赖及当前状态；实施资格取决于实际依赖满足情况。
8. **需求实施计划**：按阶段记录具体步骤、关联 REQ-ID、交付物、前置条件、执行状态和阶段完成条件；确认、设计、代码、验证、部署按需要组织，不强制每个需求都包含无关阶段。
9. **验收标准与验证计划**：为需求及阶段写可检查的结果、验证方法、适用环境和证据；缺少实库或联调时保留未验收状态。
10. **风险、回滚与决策记录**：相关旧功能风险、不可逆操作、必要的撤回方式，以及关键方案的依据、取舍和确认结果。
11. **计划变更记录**：仅记录范围、关键方案、版本及里程碑调整的日期、原因和结果；不复制聊天和详细代码变更。

## 待补充影响等级与实施门槛

这里的 P0–P3 表示“不明确事项的影响等级”，不是需求优先级：

| 等级 | 判断 | 实施门槛 |
| --- | --- | --- |
| P0 | 核心目标、数据归属、权限/安全边界或不可逆操作缺少关键依据，继续可能造成严重错误 | 禁止实施受影响需求及其依赖项；若影响整个方案，则整份计划暂停实施 |
| P1 | 会改变设计、接口或关键验收，但影响范围可定位 | 确认后才能实施相关部分，其余独立且已获授权的事项可继续 |
| P2 | 局部影响，处理可逆且不改变关键业务契约 | 可在已有授权内使用明确记录的假设，注明验证/纠正方式 |
| P3 | 非当前验收必需的优化或补充 | 记录为后续项，不阻塞当前实施 |

将清单标为“可立即实施”前，核对范围已明确、依赖已满足、没有关联未解决 P0/P1，并已有对应实施授权。记录计划本身不增加实施授权；当前会话已授权的内容不重复请求批准。清单中的阻塞编号必须能定位到待补充项或前置依赖，解决问题后同步更新清单、阶段和验收安排。

## 维护与索引

- 在真实进度、确认结果或来源变化时更新已有计划，不只刷新时间戳。
- 普通进度/澄清更新不生成新版本；实质性改版时旧版标为 `superseded`，新版说明继承、新增、调整及取消的需求。
- 索引简介描述该文件覆盖的需求，避免只写“本轮任务”；没有实际计划文件时保持表格为空，不恢复用户删除的计划或从历史记录自动重建。
- 计划与材料或实现冲突时明确列差异，不改事实来迎合计划。完成范围以用户已确认的需求和验收条件为准。
