# Model Implement Fix

## 概述

这个 skill 用于修复已经存在的问题，而不是做全新功能实现。它的重点是先诊断、再做最小安全修复，并把根因、影响范围、修复结果和验证结果沉淀下来，避免同类问题重复排查。

## 触发与交付速查

- 触发词：修复问题、bug、回归、接口偏差、权限错误、状态流转错误、按原型修复、`issue.md`、`fix-result.md`。
- 必要输入：问题描述、复现线索或日志、相关模块/页面/接口、知识库入口和命中资料、已有方案或当前实现预期。
- 必须产出：`reports/issues/<问题名>/issue.md`、`fix-result.md`、最小修复改动、验证结果和剩余风险。
- 交接出口：若判断为新功能缺口，停止并推荐回到 `model-implement` 或 `model-implement-executor`，不把缺口当 bug 修。

## 工作区

统一使用 `.codex/model-implement/` 作为共享工作区：

- `reports/init-airead/shared-context.md`、`reports/init-airead/business-flows.md`、`reports/init-airead/db-assessment.md`、`reports/init-airead/input-materials.md`：用于理解项目、业务、数据库、输入材料归类和现有约束。
- `reports/init-read/功能模块清单.md`、`reports/init-read/待人工确认.md`：仅在需要确认页面归属、材料来源、人工待确认项或用户侧表述时读取。
- `reports/modules/<模块名>/module-readiness.md`、`module-relations.md`、`frontend-plan.md`、`backend-plan.md`：用于确认问题对应的已知实现预期。
- `reports/issues/<问题名>/issue.md`：问题记录、根因分析、影响范围、修复方案与待确认项。
- `reports/issues/<问题名>/fix-result.md`：实际改动、验证结果、剩余风险与后续建议。
- `prototypes/<模块名>/`：仅在视觉、布局、交互一致性问题，或用户明确要求按原型修复时读取。
- `library/定义规则.md`：修复前强制读取的知识库入口。
- `library/` 下由 `定义规则.md` 命中的具体规则、组件、样式、SQL 或特殊资料路径：修复前必须读取并严格遵守。
- `memory/fix.jsonl`：问题修复阶段的观察、经验和规则候选。
- `memory/fix-rules.md`：问题修复阶段沉淀出的私有稳定规则。
- `memory/shared-memory.md` 与 `memory/shared-rules.md`：跨 skill 共享记忆与共享规则。

## 工作流程

1. 若存在，先读取 `memory/fix-rules.md`、`memory/shared-rules.md` 和 `memory/shared-memory.md`。
2. 执行知识库门禁：读取 `library/定义规则.md`，判断当前修复命中的强制规则和用到时查询路径，读取所有命中的具体资料，并记录本次实际参考路径。
3. 读取问题描述、复现线索、报错信息、日志、截图、相关代码路径和现有报告，判断问题是否属于“已有实现的修复问题”。
4. 使用 `scripts/issue_doc_bootstrap.py` 为当前问题创建或刷新 `reports/issues/<问题名>/issue.md` 与 `fix-result.md`。
5. 先完成问题分类，参考 `references/issue-classification-checklist.md`，明确它属于视觉、交互、数据、权限、接口、状态、性能、回归或其他哪类问题。
6. 根据问题类型判断是否需要参考原型：默认不看原型；只有视觉、布局、交互一致性问题，或用户明确要求按原型修复时才读取对应原型。
7. 按依据优先级确认期望行为：用户最新明确指令、知识库规则、已确认的问题描述、已确认方案文档、业务/数据库上下文、必要时的原型图、当前代码真实实现。
8. 复现问题并定位根因，记录影响范围、上下游模块影响、是否属于局部问题还是系统性问题。
9. 按“最小安全修复”原则和知识库命中规则修改代码；若问题实质上是需求未定义、方案缺失或功能根本未实现，应停止并建议回到 `model-implement` 或 `model-implement-executor`。
10. 按 `references/fix-validation-checklist.md` 做针对性验证，并在需要时补充回归检查。
11. 更新 `issue.md` 和 `fix-result.md`，写入稳定结论、知识库参考路径、修复结果、验证结果、剩余风险与待确认项。
12. 将有价值的问题修复观察或规则候选写入 `memory/fix.jsonl`，把稳定规则提升到 `memory/fix-rules.md`；共享规则合成默认仍由 `model-implement-init` 负责。

## 🔴 CHECKPOINT · 修复门禁

修复代码前，必须先判断这是不是“已有实现的问题修复”。遇到以下情况要停止并等待确认：

- 问题本质是新功能未实现、方案缺失或需求未定义。
- `library/` 存在但 `定义规则.md` 缺失、命中资料缺失或规则冲突。
- 问题无法复现，且现有日志、截图、接口返回或代码路径不足以定位。
- 用户要求绕过权限、数据范围、状态流转或知识库强制规则。
- 修复会影响多个模块、共享组件或公共接口，但影响范围尚未确认。

## 失败分支与兜底

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 问题分类不清 | 读取 `issue-classification-checklist.md`，按视觉、接口、权限、状态、性能等归类 | 保持 `issue.md` 为 `draft`，列出需要用户补充的信息 |
| 无法复现 | 用日志、截图、请求参数和相关代码做静态定位 | 标记 `reproducing`，不写“已修复” |
| 知识库规则冲突 | 写明冲突规则、用户要求和影响 | 停止修复，等待用户指定优先级 |
| 需要原型但找不到 | 先依据已确认方案和当前实现描述差异 | 将 UI 结论标为待确认，不做视觉猜测 |
| 最小修复牵涉公共能力 | 列出影响模块和回归范围 | 降级为修复方案说明，等待确认后再改 |

## 输入与依据规则

- 优先读取已经存在的方案文档和问题描述，不要一上来就重新解析全部项目。
- 知识库是修复前强制门禁，不是可选参考；必须先读 `library/定义规则.md`，读取命中的具体资料，并严格遵守。
- 若 `library/` 存在但 `定义规则.md` 缺失、命中规则无法读取、规则与用户指令/项目约定冲突且无法判断优先级，应停止并暴露问题，不能直接修改代码。
- 若 `library/` 完全不存在，也必须在回复和修复文档中说明“未发现知识库”，并等待用户确认是否允许在无知识库约束下继续。
- 原型图是可选输入，不是默认输入。
- 只有满足以下任一条件时才读取原型：
  - 问题属于视觉、布局、间距、颜色、层级、控件组合、界面还原或交互一致性问题。
  - 用户明确说“按原型修复”“和原型保持一致”“界面偏了”。
  - 现有方案文档无法明确界面期望表现，而当前问题又明显涉及界面呈现。
- 如果问题是纯后端、接口、权限、数据、事务、状态流转、性能、日志报错等，一般不要读取原型。
- 如果一开始判断不需要原型，但修复过程中发现缺少界面期望依据，可以升级为需要参考原型。

## 输出约束

- `issue.md` 应记录问题概述、分类、复现信息、期望行为依据、实际行为、影响范围、根因分析、修复方案、待确认项。
- `fix-result.md` 应记录实际改动、修改文件、验证结果、修复验证清单、剩余风险和建议下一步。
- 问题报告和修复结果默认用中文编写，便于使用人阅读。
- 对于已经确认的根因和修复结果，要写成稳定事实，而不是临时口语备注。
- 如果问题尚未复现或依据不足，不要假装已修复；状态必须遵循 `references/status-contract.md`，例如保持为 `draft`、`reproducing`、`diagnosed` 或 `blocked`。

## 边界

- 不要把“新功能还没做”当成问题修复；这类情况应回到 `model-implement` 或 `model-implement-executor`。
- 不要绕过知识库门禁直接修复；必须先读 `library/定义规则.md`，读取命中的具体资料，并严格遵守。
- 如果知识库入口缺失、命中资料缺失、规则冲突或优先级不清，不能直接改代码，必须先暴露并等待用户确认。
- 不要在业务规则缺失、方案冲突未解决时硬修；应先暴露冲突点。
- 不要默认参考原型，除非问题类型或用户要求触发。
- 不要为了解决局部问题引入超出必要范围的大规模改动。
- 不要覆盖用户已有改动或不相关工作。
- 不要把密钥、账号、连接串、生产数据或原始隐私数据写入记忆。

## 反模式黑名单

- 不要把“还没开发”包装成 bug 修复。
- 不要在未复现、未定位或依据不足时宣称修好了。
- 不要为局部问题扩大到重构架构、迁移框架或重写模块。
- 不要默认读取原型；只有问题类型触发或用户明确要求时才读取。
- 不要把临时调试口径、密钥、账号或生产数据写进问题文档和记忆。

## 记忆规则

参见 `references/memory-cycle.md`。简要规则如下：

- 问题修复阶段的观察、经验和规则候选写入 `memory/fix.jsonl`。
- 只有重复出现、用户确认或经验证稳定的修复规则，才提升到 `memory/fix-rules.md`。
- 读取共享规则用于对齐，但不要在本 skill 中重写其他 skill 的私有规则。
- 只有确实会反向约束初始化、页面规划或代码实施的修复规则，才标记 `shared_candidate=true`，并且要谨慎使用。
- 共享规则合成默认仍交给 `model-implement-init`，除非用户明确要求当前就刷新共享记忆。
