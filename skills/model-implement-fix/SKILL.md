# Model Implement Fix

## 概述

这个 skill 用于修复已经存在的问题或小范围实现偏差，而不是做全新功能规划或整模块开发。它的重点是轻量诊断、按需补上下文、做必要范围修复，并把真正有复用价值的根因、项目认知和修复经验沉淀到 memory。

fix 不要求项目已经完整初始化，也不要求一定存在 `model-implement` 方案。拿到一个陌生项目只修几个小问题时，应先从用户描述、日志、复现路径和相关代码入手；只有当前问题确实需要时，再查询知识库、信息库、RAG、初始化报告、方案、SQL 或原型。

## 触发与交付速查

- 触发词：修复问题、bug、回归、接口偏差、权限错误、状态流转错误、按原型修复、`issue.md`、`fix-result.md`。
- 必要输入：问题描述、复现线索或日志、相关模块/页面/接口、相关代码路径或可定位线索；知识库、初始化报告、方案、SQL、原型和 RAG 都是按需输入。
- 必须产出：必要范围修复改动、验证结果或未验证原因、核心根因与剩余风险说明；有复用价值时写入 `memory/fix.jsonl`，发现项目基础信息时补充 init-read 报告。
- 交接出口：若判断为新功能缺口，停止并推荐回到 `model-implement` 或 `model-implement-executor`，不把缺口当 bug 修。

## 工作区

统一使用 `.codex/model-implement/` 作为共享工作区：

- `reports/init-read/初始化契约.md`、`代码及框架信息.md`、`已有功能模块信息.md`、`待办清单.md`、`业务理解.md`、`数据库审查报告.md`、`待确认点.md`：如果存在，可用于理解项目、业务、数据库、材料归类、已有界面和现有约束；如果不存在，不阻塞普通问题修复。
- 旧的 `reports/init-airead/shared-context.md`、`business-flows.md`、`db-assessment.md` 仅作为历史辅助输入，不替代新版初始化主报告。
- `reports/modules/<模块名>/module-readiness.md`、`module-relations.md`、`frontend-plan.md`、`backend-plan.md`：用于确认问题对应的已知实现预期。
- `reports/issues/<问题名>/issue.md`：可选问题记录。仅在用户要求、问题复杂、跨模块、需要审计留痕或修复失败需要沉淀过程时生成。
- `reports/issues/<问题名>/fix-result.md`：可选修复结果。仅在用户要求、问题复杂、需要审计留痕或后续交接时生成。
- `prototypes/<模块名>/`：仅在视觉、布局、交互一致性问题，或用户明确要求按原型修复时读取。
- `library/定义规则.md`：按需读取的知识库入口。只有当前问题涉及不确定规则、组件、样式、SQL、权限、业务约定或公共能力时才查询。
- `library/` 下由 `定义规则.md` 命中的具体规则、组件、样式、SQL 或特殊资料路径：按需读取并严格遵守。
- `memory/fix.jsonl`：问题修复阶段的观察、经验和规则候选。
- `memory/fix-rules.md`：问题修复阶段沉淀出的私有稳定规则。
- `memory/shared-memory.md` 与 `memory/shared-rules.md`：跨 skill 共享记忆与共享规则。

## 工作流程

1. 若存在，先轻量读取 `memory/fix-rules.md` 和 `memory/shared-rules.md`；`shared-memory.md` 只在问题涉及跨阶段上下文时读取。
2. 读取问题描述、复现线索、报错信息、日志、截图、相关代码路径和用户给出的当前期望，先判断问题是否属于“已有实现的问题修复”或“小范围改动”。
3. 先完成问题分类，参考 `references/issue-classification-checklist.md`，明确它属于视觉、交互、数据、权限、接口、状态、性能、回归、构建/配置或其他哪类问题。
4. 判断是否需要额外上下文：普通语法错误、字段拼错、明显空指针、简单接口路径错误等，可直接读代码定位；权限、状态、SQL、公共组件、业务规则、跨模块影响、原型一致性等，再按需查询知识库、RAG、初始化报告、方案、SQL 或原型。
5. 需要知识库时再读取 `library/定义规则.md`，按当前问题关键词查命中资料并严格遵守；不需要时不要为了流程而查。
6. 需要初始化或历史上下文时，优先用 `model-context-rag` 定位，再打开命中的原始报告；RAG 不可用时直接读取相关 init-read/module/memory 原文。没有初始化材料时不阻塞修复。
7. 根据问题类型判断是否需要参考原型：默认不看原型；只有视觉、布局、交互一致性问题，或用户明确要求按原型修复时才读取对应原型。
8. 按依据优先级确认期望行为：用户最新明确指令、当前问题描述与复现路径、当前代码真实实现、必要时的知识库规则、已确认方案文档、业务/数据库上下文、原型图。
9. 复现或静态定位问题并定位根因，评估影响范围、上下游模块影响、是否属于局部问题还是系统性问题。
10. 按“必要且受控范围修复”原则修改代码；若问题实质上是需求未定义、方案缺失或功能根本未实现，应停止并建议回到 `model-implement` 或 `model-implement-executor`。
11. 按 `references/fix-validation-checklist.md` 做针对性验证，并在需要时补充回归检查。
12. 默认不生成 `issue.md` 和 `fix-result.md`；只有用户要求、问题复杂、跨模块、需要审计留痕或需要长线交接时，才使用 `scripts/issue_doc_bootstrap.py` 创建或更新问题报告。
13. 将有价值的问题修复观察、根因模式、项目基础认知或规则候选写入 `memory/fix.jsonl`；把稳定规则提升到 `memory/fix-rules.md`。
14. 修复过程中发现的项目基础信息，应补充到对应 init-read 报告；如果报告不存在，可创建简短条目并标记“修复过程中发现，待初始化阶段复核”。共享规则合成默认仍由 `model-implement-init` 负责。

## 🔴 CHECKPOINT · 修复门禁

修复代码前，必须先判断这是不是“已有实现的问题修复”。遇到以下情况要停止并等待确认：

- 问题本质是新功能未实现、方案缺失或需求未定义。
- 当前问题明确需要知识库约束，但 `library/` 存在且 `定义规则.md` 缺失、命中资料缺失或规则冲突。
- 问题无法复现，且现有日志、截图、接口返回或代码路径不足以定位。
- 用户要求绕过权限、数据范围、状态流转或知识库强制规则。
- 修复会影响多个模块、共享组件或公共接口，但影响范围尚未确认。

## 失败分支与兜底

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 问题分类不清 | 读取 `issue-classification-checklist.md`，按视觉、接口、权限、状态、性能等归类 | 保持 `issue.md` 为 `draft`，列出需要用户补充的信息 |
| 无法复现 | 用日志、截图、请求参数和相关代码做静态定位 | 标记 `reproducing`，不写“已修复” |
| 需要知识库但规则冲突 | 写明冲突规则、用户要求和影响 | 停止修复，等待用户指定优先级 |
| 需要原型但找不到 | 先依据已确认方案和当前实现描述差异 | 将 UI 结论标为待确认，不做视觉猜测 |
| 最小修复牵涉公共能力 | 列出影响模块和回归范围 | 降级为修复方案说明，等待确认后再改 |

## 输入与依据规则

- 优先读取用户问题、日志、复现线索和相关代码，不要一上来就重新解析全部项目。
- 初始化报告、模块方案、RAG、SQL、原型、知识库都是按需输入；不存在时不阻塞普通修复。
- 知识库不是每次修复的强制门禁。先判断是否需要：涉及权限/数据范围/状态流转/公共组件/SQL 兼容/样式规范/业务规则不清时再查。
- 若当前问题需要知识库，但 `library/` 存在且 `定义规则.md` 缺失、命中规则无法读取、规则与用户指令/项目约定冲突且无法判断优先级，应停止并暴露问题，不能直接修改相关风险代码。
- 若 `library/` 完全不存在，普通修复可以继续；只需在最终回复或 memory 中说明本轮未使用知识库。
- 原型图是可选输入，不是默认输入。
- 只有满足以下任一条件时才读取原型：
  - 问题属于视觉、布局、间距、颜色、层级、控件组合、界面还原或交互一致性问题。
  - 用户明确说“按原型修复”“和原型保持一致”“界面偏了”。
  - 现有方案文档无法明确界面期望表现，而当前问题又明显涉及界面呈现。
- 如果问题是纯后端、接口、权限、数据、事务、状态流转、性能、日志报错等，一般不要读取原型。
- 如果一开始判断不需要原型，但修复过程中发现缺少界面期望依据，可以升级为需要参考原型。

## 输出约束

- 默认最终回复即可说明问题、根因、修复、验证和剩余风险；不要为了每个小问题创建报告。
- `issue.md` 和 `fix-result.md` 只在用户要求、问题复杂、跨模块、需要审计留痕或需要交接时生成。
- 如果生成问题报告和修复结果，默认用中文编写，便于使用人阅读。
- 对于已经确认的根因和修复结果，要写成稳定事实，而不是临时口语备注。
- 如果问题尚未复现或依据不足，不要假装已修复；状态必须遵循 `references/status-contract.md`，例如保持为 `draft`、`reproducing`、`diagnosed` 或 `blocked`。
- 有复用价值的核心问题、根因模式、项目认知和验证经验优先写入 `memory/fix.jsonl`，不要把完整流水账写进问题报告。

## 边界

- 不要把“新功能还没做”当成问题修复；这类情况应回到 `model-implement` 或 `model-implement-executor`。
- 不要每次修复都强制查知识库；先判断是否需要。
- 当前问题需要知识库约束时，不要绕过知识库直接修复；必须读取 `library/定义规则.md` 和命中的具体资料。
- 如果必要知识库入口缺失、命中资料缺失、规则冲突或优先级不清，不能直接改相关风险代码，必须先暴露并等待用户确认。
- 不要在业务规则缺失、方案冲突未解决时硬修；应先暴露冲突点。
- 不要默认参考原型，除非问题类型或用户要求触发。
- 不要为了解决局部问题引入超出必要范围的大规模改动。
- 不要覆盖用户已有改动或不相关工作。
- 不要把密钥、账号、连接串、生产数据或原始隐私数据写入记忆。

## 反模式黑名单

- 不要把“还没开发”包装成 bug 修复。
- 不要在未复现、未定位或依据不足时宣称修好了。
- 不要为局部问题扩大到重构架构、迁移框架或重写模块。
- 不要因为缺少初始化报告或 implement 方案就拒绝普通小 bug 修复。
- 不要为了简单问题默认查询全套知识库、RAG、初始化报告和原型。
- 不要默认生成 `issue.md` 和 `fix-result.md` 这种低价值流水账。
- 不要默认读取原型；只有问题类型触发或用户明确要求时才读取。
- 不要把临时调试口径、密钥、账号或生产数据写进问题文档和记忆。

## 记忆规则

参见 `references/memory-cycle.md`。简要规则如下：

- 问题修复阶段的观察、经验和规则候选写入 `memory/fix.jsonl`。
- 修复过程中发现的项目基础事实，可以补充到 `reports/init-read/代码及框架信息.md`、`已有功能模块信息.md`、`业务理解.md` 或 `数据库审查报告.md`；如果是未复核观察，应标记“修复过程中发现，待初始化阶段复核”。
- 只有重复出现、用户确认或经验证稳定的修复规则，才提升到 `memory/fix-rules.md`。
- 读取共享规则用于对齐，但不要在本 skill 中重写其他 skill 的私有规则。
- 只有确实会反向约束初始化、页面规划或代码实施的修复规则，才标记 `shared_candidate=true`，并且要谨慎使用。
- 共享规则合成默认仍交给 `model-implement-init`，除非用户明确要求当前就刷新共享记忆。
