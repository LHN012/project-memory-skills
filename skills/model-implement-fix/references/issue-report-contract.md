# Issue Report Contract

`model-implement-fix` 默认不需要为每个小问题生成报告。普通 bug、小改动和清晰根因修复，直接在最终回复说明问题、修复、验证和剩余风险，并把有复用价值的核心信息写入 `memory/fix.jsonl`。

只有在以下情况才把问题修复过程沉淀成中文文档：

- 用户明确要求生成问题记录或修复结果。
- 问题复杂、跨模块、影响公共能力或需要多轮定位。
- 需要审计留痕、交接给他人或后续人工确认。
- 修复失败或暂时 blocked，需要保存诊断现场。

可选文档路径：

- `reports/issues/<issue-name>/issue.md`
- `reports/issues/<issue-name>/fix-result.md`

## issue.md

`issue.md` 是问题分析主文档，建议至少包含以下章节：

- `状态`
- `问题概述`
- `问题分类`
- `按需资料查询`
- `是否需要参考原型`
- `输入与依据`
- `复现信息`
- `期望行为`
- `实际行为`
- `影响范围`
- `根因分析`
- `修复方案`
- `待确认项`

要求：

- `问题分类` 要引用 `issue-classification-checklist.md` 的分类结果。
- `按需资料查询` 要列出本次是否查询 knowledge-library、model-context-rag、初始化报告、方案、SQL 或原型；没查的要简要说明“不需要”的理由，不要为了流程补查。
- 如果查询了知识库，必须列出是否读取 `library/定义规则.md`、实际命中的知识库路径、必须遵守的规则、是否存在冲突和处理结论。
- `是否需要参考原型` 必须写清 `是` / `否` / `待判断` 以及理由。
- `期望行为` 要写明依据来源，不要只写主观判断。
- `影响范围` 至少覆盖页面、接口、上下游模块、权限或数据链路中的相关项。

## fix-result.md

`fix-result.md` 是实际修复结果文档，建议至少包含以下章节：

- `状态`
- `修复摘要`
- `按需资料查询`
- `实际改动`
- `修改文件`
- `验证结果`
- `修复验证清单`
- `剩余风险`
- `后续建议`

要求：

- `验证结果` 应说明执行过哪些检查、测试或手工验证。
- `按需资料查询` 应说明本次是否查询知识库、RAG、初始化报告、方案、SQL、原型；如果查询知识库，应说明是否严格遵守命中的知识库规则；如存在冲突，应写清用户确认或阻塞原因。
- `修复验证清单` 应按 `fix-validation-checklist.md` 逐项记录 `适用/不适用/待补充/失败`。
- `剩余风险` 只写仍然真实存在的问题，不要写成空洞提醒。

## Memory First

对后续真正有用的信息，优先写入 `memory/fix.jsonl`，而不是堆在问题报告里：

- 可复用根因模式。
- 常见定位路径。
- 项目结构、框架、接口、权限、SQL、路由、组件等基础事实。
- 经验证的修复做法。
- 需要反向影响初始化、规划或实施阶段的经验。

不要写入：

- 一次性流水账。
- 大段日志、源码或 SQL。
- 未确认猜测。
- 密钥、账号、连接串、生产数据或隐私数据。

## 状态建议

问题修复文档状态以 `references/status-contract.md` 为准。`issue.md` 可使用 `draft`、`blocked`、`reproducing`、`diagnosed`、`fixing`、`fixed`；`fix-result.md` 可使用 `draft`、`blocked`、`fixing`、`fixed`。
