# Model Implement Reuse Workflow

## 目标

`model-implement-reuse` 用于把当前项目，或外部指定项目路径中的某块能力，沉淀成可复用、可迁移、可复盘的资产文档，并在用户明确允许时执行最小必要的抽离或重构。

## 典型输入

- 当前项目中的某个公共组件、页面区块、服务封装、工具函数或业务流程子链路。
- 用户给出的外部项目路径，例如 `E:\path\to\other-project`。
- 用户给出的功能范围，例如“订单列表中的筛选条与表格组合”“购物车结算流程”“统一上传组件”。
- 必要时的原型图、截图、需求说明、接口文档和 SQL。

## 模式决策

- `study`：
  - 默认模式。
  - 只分析、归纳和输出复用文档。
  - 不默认修改当前项目，也不默认修改外部来源项目。
- `extract`：
  - 只有在用户明确说“可以抽出来”“可以重构”“可以提取成公共组件/公共能力”时才使用。
  - 只做最小必要的代码变更，避免借抽离之名扩大范围。

## 标准流程

1. 读取 `memory/reuse-rules.md`、`memory/shared-rules.md` 和 `memory/shared-memory.md`。
2. 明确资产名、资产类型、来源路径、功能范围和工作模式。
3. 运行 `scripts/reuse_doc_bootstrap.py` 创建缺失文档。
4. 只读取与目标资产强相关的目录、文件、组件树、接口和样式，避免泛化扫描。
5. 如果目标是 UI 组件或视觉模式，必要时补读原型或截图，确认视觉契约。
6. 用 `references/reuse-decision-checklist.md` 判断是否真的值得复用。
7. 更新 `overview.md`，写清来源、价值、边界和耦合点。
8. 更新 `contract.md`，写清输入输出、依赖、状态、扩展点和禁用范围。
9. 更新 `adoption-guide.md`，写清当前项目复用方式、跨项目参考方式、适配点和验证清单。
10. 如果模式是 `extract` 且用户明确批准，再执行最小必要的抽离或重构。
11. 记录复用经验到 `memory/reuse.jsonl`，稳定后提升到 `memory/reuse-rules.md`。

## 外部项目路径规则

- 外部指定项目路径默认只作为“研究来源”。
- 分析文档默认写回当前工作区 `.codex/model-implement/reuse/`。
- 除非用户明确说可以修改该来源路径，否则不要对来源路径做代码变更。
- 如果用户希望“从 A 项目学习，再在 B 项目落地”，优先把 A 当来源，把 B 当目标，并在 `adoption-guide.md` 中拆开写。

## 原型规则

- 默认不强制读取原型。
- 只有以下情况才建议把原型或截图纳入输入：
  - 目标资产是视觉组件、页面区块或交互模式。
  - 当前实现中缺少明确样式依据。
  - 用户明确要求“按原型沉淀成公共组件”。
- 纯后端逻辑、接口编排、权限处理、状态流和数据处理通常不需要原型。

## 收尾标准

- `study` 模式结束条件：三份文档已能清晰说明“来源、契约、接入方式和边界”。
- `extract` 模式结束条件：最小必要代码改动已完成，复用文档同步更新，并明确验证结果与剩余风险。
- 如果耦合过重、边界不清或依赖不稳，应在文档中标记 `blocked` 或 `study-only`，不要强行抽公共层。
