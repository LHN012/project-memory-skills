# Model Implement Reuse

## 概述

这个 skill 用于把当前项目，或用户指定项目路径中的某块能力，沉淀成后续可以复用、迁移、复盘和讲清边界的“复用资产”。默认进入 `study` 模式，只输出复用文档与经验沉淀；只有在用户明确允许抽离、重构或提取时，才进入 `extract` 模式触达代码。

## 触发与交付速查

- 触发词：沉淀复用、公共组件、学习实现、抽离准备、跨项目复用、`overview.md`、`contract.md`、`adoption-guide.md`。
- 必要输入：资产名、资产类型、来源路径、功能范围、当前模式是 `study` 还是 `extract`。
- 必须产出：`reuse/<资产名>/overview.md`、`contract.md`、`adoption-guide.md`，以及可复用/不可复用边界。
- 交接出口：`study` 完成后停止；只有用户明确批准 `extract` 时，才进入代码抽离或重构。

## 工作区

统一使用 `.codex/model-implement/` 作为复用沉淀工作区：

- `reuse/<资产名>/overview.md`：资产来源、复用价值、耦合边界、适用范围与待确认项。
- `reuse/<资产名>/contract.md`：组件/功能/逻辑契约，包含输入输出、依赖、状态、扩展点和禁用范围。
- `reuse/<资产名>/adoption-guide.md`：当前项目接入方式、跨项目参考方式、适配点、验证清单和抽离步骤建议。
- `memory/reuse.jsonl`：复用沉淀阶段的观察、经验和规则候选。
- `memory/reuse-rules.md`：复用沉淀阶段的私有稳定规则。
- `memory/shared-memory.md` 与 `memory/shared-rules.md`：由 `model-implement-init` 统一合成的跨 skill 共享记忆与共享规则。

如果来源是外部指定项目路径，文档仍默认写回当前工作区的 `reuse/`，不要默认把文档写进来源项目。

## 工作模式

- `study`：默认模式。只做学习、拆解、归纳、对比和文档沉淀，不默认修改任何代码。
- `extract`：只在用户明确允许时使用。可以在当前项目或用户指定目标范围内，执行最小必要的公共能力抽离、封装或重构。

强制边界：

- 不要把 `study` 和 `extract` 混在一起默认执行。
- 如果用户只说“学习一下”“提炼一下”“帮我总结”，一律按 `study` 处理。
- 如果来源是外部指定项目路径，除非用户明确说“可以改这个路径里的代码”，否则只读不改。

## 工作流程

1. 若存在，先读取 `memory/reuse-rules.md`、`memory/shared-rules.md` 和 `memory/shared-memory.md`。
2. 明确本次目标的 `资产名`、`资产类型`、`来源路径`、`功能范围`、是否为当前项目，以及当前是 `study` 还是 `extract`。
3. 使用 `scripts/reuse_doc_bootstrap.py` 为当前资产创建或刷新 `overview.md`、`contract.md` 和 `adoption-guide.md`。
4. 只读取与目标资产直接相关的代码、路由、组件、样式、接口、SQL、说明文档和必要截图，不要一上来全库扫描。
5. 先判断“哪些部分值得复用”，再判断“哪些部分高度项目耦合、只适合保留在原地”。
6. 如果目标是 UI 组件、页面局部区块或样式模式，并且存在对应原型或截图，可读取原型作为视觉契约补充；若用户未提原型且问题不涉及视觉一致性，不必强制读取。
7. 更新 `overview.md`，写清资产来源、复用价值、边界、耦合点、适用范围和不建议复用的部分。
8. 更新 `contract.md`，写清公共接口、输入输出、内部状态、依赖、扩展点、数据来源、权限约束和替换点。
9. 更新 `adoption-guide.md`，写清当前项目如何接入、跨项目如何参考、需要适配哪些依赖，以及如何验证抽离结果。
10. 若处于 `extract` 模式且用户已明确批准，再执行最小必要的代码抽离或重构，同时同步更新复用文档。
11. 将有价值的复用观察和规则候选写入 `memory/reuse.jsonl`，把稳定规则提升到 `memory/reuse-rules.md`；共享规则合成默认仍由 `model-implement-init` 负责。

## 🔴 CHECKPOINT · 复用门禁

分析或抽离前，必须先确认模式和边界。遇到以下情况要停止并等待用户确认：

- 用户没有明确允许抽离、重构或提取代码，却请求会修改代码的动作。
- 来源路径是外部项目，且用户未明确允许修改该路径。
- 资产范围过宽，无法界定目标文件、组件、接口、流程或页面区块。
- 依赖边界、权限边界、状态边界或数据来源不清。
- 复用结论会影响公共组件、跨项目规则或共享记忆，但缺少验证依据。

## 失败分支与兜底

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 模式不明确 | 默认选择 `study`，只读分析并生成文档 | 不修改代码，等待用户明确进入 `extract` |
| 来源路径不可访问 | 记录路径和访问错误 | 只创建待补充的资产文档骨架 |
| 范围过大 | 要求收敛到目录、文件、组件、接口或业务子链路 | 停止全库扫描，列出建议范围 |
| 耦合过重 | 在 `overview.md` 写清项目耦合点和禁用范围 | 不抽公共层，只保留参考说明 |
| 抽离验证不足 | 运行可用测试或最小回归检查 | 在 `adoption-guide.md` 标注未验证风险 |

## 输入与依据规则

- 可以分析当前项目中的公共组件、服务层封装、工具函数、组合式业务逻辑、接口适配层或某个完整功能块。
- 可以分析用户提供的外部项目路径中的某块功能，并把结果沉淀到当前工作区。
- `功能范围` 可以是页面区块、组件树、接口组合、状态流、业务流程子链路、某个目录或某几个文件。
- 如果复用目标是视觉组件，且实现代码没有写清样式意图，优先参考已有实现和原型/截图来定义视觉契约。
- 如果目标是纯后端逻辑、服务编排、权限/状态/数据处理，一般不需要读取原型。

## 输出约束

- `overview.md` 要明确写出“可复用部分”和“项目耦合部分”，不要只写优点不写边界。
- `contract.md` 要尽量写成别的工程师可直接参考的契约说明，而不是泛泛而谈。
- `adoption-guide.md` 要同时覆盖“当前项目如何复用”和“其他项目如何参考”，并标明必须替换的依赖。
- 如果当前只能完成学习和方案沉淀，状态应按 `references/status-contract.md` 保持为 `draft` 或 `study-only`，不要假装已经完成代码抽离。
- 如果提取风险高、耦合重或依赖不清，应优先暴露阻塞点和待确认项，而不是强行抽公共层。

## 边界

- 不要默认把任意重复代码都抽成公共组件或公共库。
- 不要把一次性业务特殊分支包装成“可复用能力”。
- 不要在依赖边界、权限边界、状态边界不清时做大规模重构。
- 不要因为想复用，就擅自修改不在本次范围内的模块。
- 不要把外部项目的源码大段复制到记忆文件中。
- 不要把密钥、账号、连接串、生产数据或原始隐私数据写入复用文档或记忆。

## 反模式黑名单

- 不要把 `study` 和 `extract` 混在一起执行。
- 不要把重复代码直接等同于可复用资产。
- 不要把一次性业务特殊分支包装成公共能力。
- 不要把外部项目源码大段复制到当前记忆或复用文档。
- 不要在依赖、权限、状态和验证边界不清时做公共抽离。

## 记忆规则

参见 `references/memory-cycle.md`。简要规则如下：

- 复用沉淀阶段的观察、经验和规则候选写入 `memory/reuse.jsonl`。
- 只有重复出现、用户确认或经验证稳定的复用规则，才提升到 `memory/reuse-rules.md`。
- 只有确实会反向约束初始化、页面规划、代码实施、问题修复或代码审查的复用规则，才建议标记 `shared_candidate=true`。
- 外部项目路径中的一次性目录命名、局部 hack 或只适用于单项目的耦合细节，不要轻易提升为共享规则。
- 共享规则合成默认仍由 `model-implement-init` 负责，除非用户明确要求当前就刷新共享记忆。
