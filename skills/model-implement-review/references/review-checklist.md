# Review Checklist

审查重点是 bug、风险、行为回归和测试缺口，不是风格挑刺。

## 必查项

1. `业务逻辑正确性`
   - 实现是否符合用户要求、方案文档和业务流程。
   - 是否把未定义需求当成默认行为实现。
2. `权限与数据范围`
   - 按钮、接口、查询、数据范围是否符合角色、组织、用户、供应商、预算主体等约束。
3. `接口契约一致性`
   - 请求字段、响应字段、分页结构、错误码、枚举值、空态口径是否一致。
4. `状态枚举与状态流转`
   - 状态判断是否完整，状态变更前置条件和后置影响是否正确。
5. `写操作事务与幂等`
   - 保存、提交、审核、删除、导入、回调等是否有重复提交、并发写、回滚和幂等风险。
6. `回归影响范围`
   - 改动是否影响相邻页面、上下游模块、列表/详情/编辑、统计、提醒、审批或导出。
7. `异常处理与空态`
   - 接口失败、无数据、无权限、字段为空、枚举未知、网络异常是否处理。
8. `性能与索引风险`
   - 查询、分页、模糊搜索、排序、聚合、跨表关联、前端重复渲染是否存在明显风险。
9. `测试覆盖与验收缺口`
   - 是否缺少正常流、异常流、权限流、状态流转流、边界流、回归流验证。
10. `UI 与方案一致性`
   - 当审查范围涉及前端 UI 时，检查布局、字段、按钮、状态、显隐和交互是否符合方案。
11. `UI 与原型一致性`
   - 仅在用户要求或 UI/交互一致性审查时检查。
12. `日志、审计、可追踪性`
   - 关键写操作、异常、状态变更是否具备必要日志或审计信息。

## 原型使用规则

- 默认不参考原型。
- 只有 UI 还原、交互一致性、页面视觉偏差审查，或用户明确要求时才参考原型。
- 纯后端、接口、权限、事务、性能类审查通常不参考原型。

## 输出要求

每条发现都应包含：

- 严重级别。
- 问题标题。
- 具体位置。
- 影响说明。
- 建议处理方式。
- 推荐后续 skill。
- 是否需要用户确认。

最后必须列出“待用户选择”清单，不能默认执行后续修复。
