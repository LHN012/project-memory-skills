# Model Implement Review

## 概述

这个 skill 用于把目标模块做成“可验证的验收型审查”。它不再只看代码或 diff，而是固定执行三步：

1. 先做前后端接口契约审查。
2. 再根据接口动作和前端交互生成待审查清单。
3. 最后用 Playwright 真实操作页面，逐项更新清单，并把具体问题写入最终审查问题清单。

本 skill 只审查、记录和建议后续处理，不默认修复代码，不自动进入 `model-implement-fix`。

## 触发与交付速查

- 触发词：审查模块、上线前验收、运行时审查、Playwright 测试、接口契约审查、交互清单、CRUD 审查、页面交互验收。
- 必要输入：目标模块、审查轮次、可访问页面或菜单路径、测试环境 URL、测试账号/权限、允许的数据操作范围、目标前后端代码范围。
- 必须产出：
  - `reports/reviews/<目标模块>-第<轮次>轮/接口契约对齐判断.md`
  - `reports/reviews/<目标模块>-第<轮次>轮/运行时待审查清单.md`
  - `reports/reviews/<目标模块>-第<轮次>轮/审查问题清单.md`
- 交接出口：审查完成后停止；用户明确选择具体问题后，才推荐进入 `model-implement-fix`、`model-implement-executor` 或 `model-implement`。

## 工作区

统一使用 `.codex/model-implement/` 作为共享工作区：

- `reports/init-read/初始化契约.md`、`代码及框架信息.md`、`已有功能模块信息.md`、`待办清单.md`、`业务理解.md`、`数据库审查报告.md`、`待确认点.md`：理解项目、业务、数据库、输入材料归类、已有页面和待确认事项。
- 旧的 `reports/init-airead/shared-context.md`、`business-flows.md`、`db-assessment.md` 仅作为历史辅助输入，不替代新版初始化主报告。
- `reports/modules/<模块名>/module-readiness.md`、`module-relations.md`、`frontend-plan.md`、`backend-plan.md`：确认页面预期、接口规划、业务闭环和验收依据。
- `reports/review-config/测试账号与环境.md`、`测试流程与要求.md`、`<模块名>-测试要求.md`：可选审查配置。有则读取，没有则正常审查；遇到登录或授权阻塞时提示用户人工授权后继续。
- `reports/reviews/<目标模块>-第<轮次>轮/接口契约对齐判断.md`：前后端接口契约对齐判断。
- `reports/reviews/<目标模块>-第<轮次>轮/运行时待审查清单.md`：待审查清单和测试进度表；只记录状态、是否报错、是否阻塞和问题编号，不写具体问题细节。
- `reports/reviews/<目标模块>-第<轮次>轮/审查问题清单.md`：最终审查问题清单、证据摘要、风险、测试缺口和待用户选择项。
- `memory/review.jsonl` 与 `memory/review-rules.md`：审查阶段观察、Playwright 控件操作经验和稳定规则。
- `memory/shared-memory.md` 与 `memory/shared-rules.md`：跨 skill 共享记忆与共享规则。

## 工作流程

1. 若存在，先读取 `memory/review-rules.md`、`memory/shared-rules.md` 和 `memory/shared-memory.md`，尤其复用已有 Playwright 控件操作经验、选择器策略和等待条件。
2. 明确目标模块、审查轮次、测试入口、环境 URL、数据操作边界和是否允许新增/修改/删除测试数据；如果用户没有提前提供账号或授权信息，不要把它当作启动阻塞。
3. 读取可选审查配置：若存在 `reports/review-config/测试账号与环境.md`、`测试流程与要求.md` 或 `<模块名>-测试要求.md`，则纳入本轮审查依据；若不存在，继续正常审查。
4. 使用 `scripts/review_doc_bootstrap.py --module <目标模块> --round <轮次>` 创建或刷新本轮三份审查文档，并确保 `reports/review-config/` 下的配置骨架存在。
5. 读取目标模块相关的初始化报告、模块关系、前后端方案、当前前端页面代码、接口文件、后端 Controller/API、DTO/VO、Service、Mapper/XML 和权限相关代码。
6. 按 `references/interface-contract-checklist.md` 先完成接口契约审查，并写入 `接口契约对齐判断.md`。在这一步不要急着打开页面测试。
7. 按 `references/review-checklist.md` 从接口动作和前端可见交互中生成 `运行时待审查清单.md`。清单必须覆盖目标模块页面内可见且启用的交互组件，并为每一项写明验收标准、验收方式和复测策略；只有达到验收标准才允许标记为 `已测通过`。
8. 执行 Playwright 测试前先完成运行时门禁：确认环境、测试数据前缀、数据清理策略和不可逆操作边界。若账号、登录或授权缺失，打开页面尝试进入；遇到登录、验证码、二次认证或权限阻塞时，停下来提示用户在浏览器中完成授权，然后继续测试。
9. 按 `references/runtime-playwright-checklist.md` 使用 Playwright 逐项操作页面。操作控件前优先参考 `memory/review-rules.md` 中已有的稳定操作套路；每测试完一项，立即更新 `运行时待审查清单.md`，只记录是否完成、是否报错、是否阻塞和对应问题编号。
10. 对增删改查业务，按 `增 -> 查 -> 改 -> 再查 -> 删/作废 -> 再查` 顺序验证。删除不可逆、影响审批/库存/账务或权限不允许时，改为记录“删除动作需人工确认”或验证软删除/作废状态。
11. Playwright 测试时同步捕获三类证据：浏览器 console 报错、network 请求失败、页面表现异常。必要时记录关键请求的 method、path、状态码和响应摘要。
12. 若用户在审查过程中补充测试账号、环境、授权方式、测试流程、测试数据规则或模块特殊要求，应同步沉淀到 `reports/review-config/` 中对应文件；不要记录真实密码、token、生产地址或敏感数据，除非用户明确要求并接受本地存储风险。
13. 具体问题只写入 `审查问题清单.md` 的发现列表，不写进 `运行时待审查清单.md` 的细节栏。清单只通过问题编号关联到发现。
14. 按 `references/review-severity.md` 给每条发现定级为 `P0`、`P1`、`P2`、`P3`。
15. 审查结束后，在 `审查问题清单.md` 输出待用户选择项，推荐后续 skill，但不自动修复。
16. 将可复用的运行时审查经验写入 `memory/review.jsonl`，尤其是 Playwright 控件探索中发现的失败方式、成功操作方式、稳定选择器和等待条件；只有重复出现或用户确认的稳定经验才提升到 `memory/review-rules.md`。

## CHECKPOINT · 审查门禁

遇到以下情况必须停止或降级为静态审查，并在三份文档中写明阻塞原因：

- 没有明确目标模块、页面入口、审查轮次或代码范围。
- 当前环境疑似生产环境，或用户未确认可以写入测试数据。
- 新增、修改、删除会影响审批、库存、账务、通知、外部系统或真实业务数据，且没有安全测试策略。
- 前后端接口契约严重缺失，导致无法构造可靠的交互清单。
- 页面需要人工验证码、外部硬件、短信、电话控件或第三方系统时，先提示用户完成授权或外部操作；若用户无法完成，再把相关项标为 `阻塞未测`。
- 用户要求审查时顺手修复问题；本 skill 只能记录和建议，需用户选择问题后再进入修复。

## 可选审查配置

审查配置不是前置条件。有则读取，没有则正常测试。

- `reports/review-config/测试账号与环境.md`：记录测试环境、账号角色、组织/数据范围、授权方式、禁止操作和数据安全边界。
- `reports/review-config/测试流程与要求.md`：记录通用测试流程、CRUD 顺序、测试数据命名、清理策略和不可逆操作规则。
- `reports/review-config/<模块名>-测试要求.md`：记录某个模块的特殊测试数据、流程、禁测动作、人工确认动作和验收口径。

如果没有配置，运行时遇到登录、授权、验证码、菜单权限或会话过期，应暂停并提示用户在浏览器中完成授权，然后继续。若用户在过程中补充了可复用的账号角色、环境、测试流程或模块要求，应写入上述配置文件。不要默认把真实密码、token、生产连接串或敏感业务数据写入配置；需要保存时必须明确标注风险和用途。

## 运行时经验记忆

Playwright 探索控件得到的经验写入 `memory/`，不要写入 `reports/review-config/`。二者边界如下：

- `reports/review-config/`：用户指定或补充的测试账号、环境、授权方式、业务流程、数据策略和模块特殊要求。
- `memory/review.jsonl`：审查过程中发现的可复用操作经验，例如某类下拉框、树控件、弹窗、表格行按钮、上传控件的失败方式和成功操作方式。
- `memory/review-rules.md`：重复出现、跨页面稳定或用户确认有效的 Playwright 操作规则，执行下一轮审查前优先读取。

记录控件操作经验时，至少写清适用范围、控件类型、失败尝试、成功步骤、选择器策略、等待条件和是否可提升为共享规则。不要记录真实账号密码、token、验证码、生产地址、敏感业务数据或一次性随机 DOM id。

## 待审查清单规则

`运行时待审查清单.md` 是测试进度表，不是问题报告。每项建议包含：

- 编号
- 页面
- 交互项
- 关联接口
- 验收标准：达到什么结果才算通过
- 验收方式：完整测试 / 微测试 / 静态确认 / 人工确认
- 测试状态：`未测` / `已测通过` / `已测有报错` / `阻塞未测` / `不适用`
- 是否报错：`是` / `否` / `不适用`
- 是否阻塞：`是` / `否`
- 问题编号：例如 `P1-001`，无问题则留空
- 复测策略：完整测试 / 微测试 / 本轮跳过 / 阻塞未测 / 人工确认

禁止在待审查清单中写具体堆栈、接口响应、错误分析或修复建议；这些只写入 `审查问题清单.md`。

`已测通过` 必须代表已经满足验收标准，而不是单纯“点击后没有报错”。上一轮或本轮已通过的条项，后续可以按复测策略选择微测试或本轮跳过；但登录、查询、新增、编辑、删除/作废、提交/审核等核心链路，以及本轮代码、接口、权限、配置或数据库变更影响到的条项，必须完整测试或至少微测试。

## 交互覆盖边界

默认必须测试目标模块页面内“可见且启用”的交互组件，包括：

- 查询、重置、筛选、日期控件、字典下拉、下拉树。
- 表格分页、排序、选择、行操作、详情跳转。
- 新增、编辑、删除、保存、提交、审核、取消、返回。
- 弹窗、抽屉、Tab、步骤切换、显隐联动、表单校验。
- 上传、下载、导入、导出、预览。
- 空态、加载态、错误态、禁用态、无权限态。

隐藏权限态、极端角色态、异常数据态和跨模块长链路可以作为扩展项；如果本轮不覆盖，必须在 `审查问题清单.md` 写入未覆盖范围。

## 问题记录规则

`审查问题清单.md` 是最终审查问题清单，按 `目标模块 + 第几轮` 命名所在目录。每条问题至少写清：

- 严重级别和编号。
- 所属页面、交互项、关联接口或代码位置。
- 问题现象。
- 证据摘要：console、network、页面表现、接口契约差异中的相关证据。
- 影响范围。
- 建议处理方式。
- 推荐后续 skill。
- 是否需要用户确认。

没有明确问题时，也要写“未发现明确问题”、已覆盖范围、未覆盖范围、残余风险和已执行的 Playwright 测试摘要。

## 反模式黑名单

- 不要跳过接口契约审查直接打开页面点按钮。
- 不要把待审查清单写成详细问题报告。
- 不要在生产或真实业务库里默认插入、修改或删除测试数据。
- 不要对不可逆删除、审批、库存、账务、外部通知等动作强行自动执行。
- 不要只看页面现象，不记录 console 和 network 证据。
- 不要把“功能未实现”直接当成 bug；应标注为实施缺口并推荐合适 skill。
- 不要自动修复审查发现。
